## 「总结错误经验」按钮接回既有纠错闭环（提交 6340d4a / bc1f015）

**背景**：设置页系统提示词卡片上要加一个「自动总结错误经验」按钮。上一轮自建了一套
（宿主 `settings/summarizeToolErrors` + 日志包注入 `deployment:error-lessons`），
而仓库里 `packages/guard/command-correct-errors`（`/correct-errors` 命令）与
`packages/guard/error-reflection-prompt` 早就是完整的一套。两套并存 = 同名段落注册两次
= 插件树加载即抛错。用户决策：**复用现有的，保证能用，最小修改**。

**最终形态**（三条链路，各司其职）：

| 组件 | 职责 |
|---|---|
| `tool-error-journal` | 只记录：监听 `session/event` 写 `~/.dsh/tool-error-log.jsonl` |
| `command-correct-errors` | `/correct-errors`：读日志 + 反思文档 → 起后台子代理重写文档 → 日志原文追加进 `tool-error-log-archive.jsonl` → 清空日志 |
| `error-reflection-prompt` | 装配时读 `~/.dsh/error-reflections.md`，注入 `deployment:error-lessons` 段 |
| 卡片按钮 | 只调用 `/correct-errors`，把回执显示出来 |

**关键坑（最容易再犯）**：`ctx.remote.session.prompt({content:[{type:'text',text:'/correct-errors'}]})`
**不会执行命令**，它只是把这段文本当普通消息送给模型。表征：会话起了一轮、`turnOutline`
里 prompt 就记着 `/correct-errors`、模型还调了工具、stats 涨到 8 步/111 秒 —— handler 一次没进。
正确通道是 `ctx.remote.commands.execute(sessionId, line, [])`（参考实现
`packages/client/ui-commands/src/client/service.ts`），返回值 `CommandExecution.result.text`
就是命令自己的回执。

**改动文件**：`packages/client/ui-settings-plugins/src/client/{index.ts,prompt-overrides-card-controller.ts,PromptOverridesCard.tsx,locales.ts}`、
`packages/api/settings-controller/src/{index.ts,types.ts}`（删 `reflections.ts`）、
`packages/guard/tool-error-journal/src/{index.ts,documents.ts}`。

**验证口径**：179 个单测通过；`tsc -b tsconfig.client.json` 改动包零报错；真机
（`dsh --profile web`）用探针条目跑通「命令 → 归档 → 清空 → 后台重写文档」，事后按字节
快照还原用户数据。

## 项目环境备注（本机）

- **启动 web**：`DEEPSEEK_API_KEY=… env -u NODE_OPTIONS node --import tsx/esm apps/cli/src/bin.ts --profile web`。
  必须 `env -u NODE_OPTIONS`：WorkBuddy 注入的 safe-delete shim 会把 dsh 自己的锁文件清理
  算进删除配额，启动直接失败。被杀进程会留下 `~/.dsh/.credentials.yaml.lock`（内容为 PID），
  确认 PID 已死再删该文件，否则 `timed out waiting for the writer lock`。
- **客户端插件不走 vite 打包**：`apps/web/dist` 只有外壳，插件由宿主按
  `/plugins/??<pkg>/client.js&rev=<hash>` 提供，改插件只需重建 `tsdown --env.DSH_BUILD_FACE client`。
- **web RPC 调试**：先 `curl -c cookies.txt "http://127.0.0.1:3080/?token=<启动日志里的 token>"`（303 + `set-cookie`），
  再 POST `/api/<method>`，body 形如 `{"type":"client-request","rpcId":…,"method":…,"payload":{"args":{…}}}`。
  token 一次性，服务重启即失效。脚本在 `tmp/cu-verify/rpc.mjs`。
- **RPC 字段名按 descriptor 对账，别按源码参数名猜**：`settings/readPromptSections` 的线上字段名是 `cwd`（源码参数叫 `workspace`）。
- **会话数据是分帧 `zstd`**：`zlib.zstdDecompressSync` 只解第一帧（仅得文件头约 211 字符）；
  看会话状态优先用 `session/list` 的 `turnOutline`/`sessionStats`。
- **`oxlint` 既有错误**：`packages/client/ui-settings-plugins/src/client/index.ts` 的 `loadSkills`
  里有 5 个 `no-unnecessary-condition`（`ctx.locale.getSnapshot?.()` 防御性可选链），
  改动它会影响运行时语义，未处理；`tests/llm-retry-card-controller.spec.ts` 有 2 个类型错误（既有）。
