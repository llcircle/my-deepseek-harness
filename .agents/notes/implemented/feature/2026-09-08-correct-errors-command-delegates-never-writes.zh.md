# Agent Note: The correction command delegates, never writes

Status: implemented

[English](2026-09-08-correct-errors-command-delegates-never-writes.md) | 中文

## Problem

工具错误日志记录了失败但本身不解决问题，人工复盘又难以扩展。纠错流程需要模型工作——根因分析与书面反思——但这项工作不能搭在主对话上：它应当由用户的显式动作启动，并在后台运行。

## Decision

`/correct-errors` 是只读命令：它读取最新的日志条目（有界、从旧到新），经委托接缝启动恰好一个一次性子代理并附带反思提示词，随即返回子代理运行 id。所有变更都归子代理——提示词指示它总结原因与修复，并用它自己的 write 工具向配置的文档追加带日期的反思分节，因此这次写入与任何其他工具使用一样受子代理的工具、沙箱与审批约束。缺少 subagent 运行时或提供方、或日志不可读时，命令显式失败；空日志则成功且不启动子代理。

## Alternatives considered

- **由命令处理器直接写反思。** 拒绝：处理器运行时不带模型轮次，"AI 总结"会退化为模板文本；反思需要真正的模型推理，而这正是委托接缝提供的。
- **用纠错提示词 steer 主对话。** 拒绝：那会劫持用户正在使用的主线并使反思变成同步操作；需求是后台、独立的处理。
- **每 N 次失败自动触发。** 本包拒绝：按阈值静默启动后台子代理会让高日志量的部署措手不及；已记录的开放方向保留同一提示词构造器，等待将来的显式选择。

## Consequences

- 一次用户动作得到一份持久反思文档，且不触碰主对话；每次纠错都在 subagent 表面上有自己的会话，可见可查。
- 两次调用会启动两个都向文档追加的子代理；去重与完成通知仍是 subagent 表面的职责。
- 命令依赖日志的 JSONL 形状；会话日志仍是权威记录，本日志自身也派生自它。
